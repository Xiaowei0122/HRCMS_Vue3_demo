# 工单插队与顺延 · 设计方案

> 状态：已评审，待实施
> 范围：报修工单的「轻重缓急插队」与「处理超时顺延」两类诉求
> 原则：排期是内部视图，客户只看自己工单上的「预计处理时间」；插队/顺延不产生客户侧连锁通知。

---

## 1. 背景与目标

1. **插队（轻重缓急）**：灾难性故障、突发领导检查等场景，某工单需立即处理，排到当天最前，其余工单顺延。
2. **超时顺延**：已接/已排工单因现场突发（故障定位耗时、安装工序多）处理时间拉长，需要标记超时并把后续工单往后挪。

核心结论：两个诉求是同一件事的两面——**「工单在工程师当天的队列里排第几、预计占多久」**。方案以「每天 5 个时段」为硬约束，`timeSlot` 本身即顺序，不引入更复杂的队列序号。

---

## 2. 核心模型

- 每天 5 个时段：`AM1 / AM2 / PM1 / PM2 / PM3`（沿用现有 `TIME_SLOTS`，[repair-status.js](../../miniprogram/src/utils/repair-status.js)）。
- 一时段一单，`timeSlot` 即顺序，**不新增 `sortOrder`**。
- 每天是硬容量上限（5 单），超出必须顺延到次日，不做多日自动级联。

### 两套视图彻底分离

| 视图 | 谁看 | 内容 | 插队/顺延时 |
|---|---|---|---|
| 排期矩阵（内部） | 管理员 / 工程师 / 调度 | 每天 5 时段、谁在哪个时段 | 内部重排，静默 |
| 工单「预计处理时间」 | 客户 | 单一字段：`预计 9月23日 上午(早) 处理` | 静默更新该字段 |

> 客户永远看不到矩阵，也收不到「时间又变了」的连锁推送；唯一感知是自己工单上的预计时间变化。

---

## 3. 权限模型（加急 = 处理权，不下放给提单人）

| 角色 | 能做什么 | 性质 |
|---|---|---|
| 客户 / 业务 | 提单时选「紧急状况」（紧急/普通/不急） | 严重程度**标签**，红标提示，**不插队** |
| 工程师 | 接单时「加急置顶」+ 接单后《优先处理》+ 当天内上下移 | **处理权**（只限自己当天队列） |
| 管理员 | 指派时勾加急 / 全局插队（跨天跨人、未接单也可） | 兜底 |

关键点：**「紧急」是客户表达的严重程度信号，人人可发；「加急/插队」是排期处理权，仅工程师与管理员可触发**。链路为：客户表达「紧急」→ 工程师掌握现场、决定是否「加急置顶」。

## 4. 数据模型变更

### 4.1 `repairs` 文档新增字段

```python
# —— 客户可见的已定处理时间（插队/顺延时静默更新）——
"scheduledDate": "",          # 已定上门日期 YYYY-MM-DD
"scheduledTimeSlot": "",      # 已定时段 key（AM1/AM2/PM1/PM2/PM3）

# —— 加急（插队）标记 ——
"escalated": False,           # 是否加急置顶
"escalateReason": "",         # 加急原因（内部审计，真实原因，客户不可见）
"escalatedBy": "",            # 触发人
"escalatedAt": "",            # 触发时间

# —— 超时（P1）——
"expectedDuration": 0,        # 预计处理时长（分钟）
"startedAt": "",              # 实际开始处理时间
"estimatedDoneAt": "",        # 预计完成 = startedAt + expectedDuration
"overdue": False,             # 是否超时（冗余便于筛选/排序）
```

> `priority` 保持现有 3 档（紧急/普通/不急）不变，作为严重程度标签；「加急」独立为 `escalated` 标记。

### 4.2 `repair_schedule` 文档

- 插队/顺延只改 `date` / `timeSlot`（重排），**不新增字段**。
- 排期变更需留审计：谁、哪几单、顺序如何变化、时间（可复用/扩展 `createdAt`+`createdBy`，或新增轻量审计集合）。

## 5. 关键流程

### 5.1 加急置顶（插队）

**触发点**（三处，均需必填原因）：
1. 工程师接单时（`accept` 弹窗勾「加急置顶」）；
2. 工程师接单后（详情《优先处理》按钮）；
3. 管理员指派时（`assign` 弹窗勾加急）或全局插队。

**规则**：
- 置顶到队首（AM1），原 AM1 起的后序各顺延一格。
- 当天满 5 时：末位（PM3）**顺延到次日最早空档**；次日也满 → 停止，转人工兜底（改更后日期或转单给其他工程师）。
- 当天内「上下移」只是重排，**不会产生第 6 个**，不涉及跨天。

### 5.2 当天内上下移（工程师自由排序）

- 操作：置顶 / 上移一位 / 下移一位。
- 边界：只动自己当天、避开锁定时段（培训/驻场/请假）、重排后保持紧凑靠前（空档沉队尾）、留审计。
- **不填原因**（只是「先处理谁、后处理谁」）。

### 5.3 跨天顺延通知（温和措辞，客户侧进度节点）

被顺延到次日的工单，在 `progress` 追加一条**固定模板**节点（不给自由输入）：

> 「因排期调整，您的工单预计将于 **9月24日 上午(早)** 上门处理，给您带来不便敬请谅解。如有疑问请联系工程师。」

- 真实原因（插队/加急）只留在内部 `escalateReason`，**绝不出现在客户可见文案**。
- 当天内重排（上午↔下午）**零通知**；仅跨天（今天→明天）追加此节点。

## 6. 后端接口清单

### P0（插队 / 排序闭环）

| 接口 | 作用 | 权限 |
|---|---|---|
| `POST /repairs/{id}/accept` 增参 `{ escalate, escalateReason }` | 接单时加急置顶 | 工程师 |
| `PATCH /repairs/{id}/assign` 增参 `{ escalate, escalateReason }` | 指派时加急置顶 | 管理员 |
| `POST /repairs/{id}/escalate` | 接单后加急置顶（`{ reason }`，管理员可带 `targetDate/targetTimeSlot` 跨天跨人） | 工程师(本人当天)/管理员 |
| `POST /repairs/{id}/reorder` | 当天内上下移（`{ direction: top/up/down }`） | 工程师(本人当天) |
| `GET /repairs/schedule` 返回 `escalated`/`overdue` | 矩阵红标展示 | 内部 |
| `_format_repair` 增 `escalated/escalateReason/scheduledDate/scheduledTimeSlot` | 详情/列表回显 | — |

### P1（超时标记 + 静默重排）

| 接口 | 作用 | 权限 |
|---|---|---|
| `POST /repairs/{id}/start` | 记录 `startedAt`（实际到场） | 工程师 |
| `POST /repairs/{id}/extend` | 排查延长（`{ reason, expectedDuration }` + 进度节点） | 工程师 |
| 超时判定 | `now > estimatedDoneAt` 且仍「处理中」→ 标 `overdue` | 系统 |
| 顺延后续 | 复用现有改派/重排能力把后序单挪后（不新增接口） | 工程师/管理员 |

## 8. 实施分期

### P0：插队 / 排序闭环（最小可用）

1. 数据字段 + `_format_repair`/`schedule` 返回新字段（老数据回填默认值）。
2. 后端：`accept`/`assign`/`escalate`/`reorder` 四个改动点 + 跨天顺延副作用（写温和节点 + 静默更新 `scheduledDate/scheduledTimeSlot`）。
3. 前端：接单弹窗加急开关 + 详情《优先处理》+ 排期排序入口 + 红标。
4. 历史数据回填脚本（`scheduledDate/scheduledTimeSlot` 从排期表反推）。

### P1：超时标记 + 静默重排

1. `expectedDuration` 默认值（售后上门 90min、协助送货 60min）+ 指派/接单时可选填。
2. `start` / `extend` 端点 + 排查节点。
3. 超时判定/矩阵红标 + 复用重排顺延后续。

### P2（可选）

- 排期拖拽、加急统计报表（超时率 / 平均时长 / 加急次数）。

## 9. 边界与风险

1. **顺延只到次日最早空档**，次日也满则停止并转人工，不自动级联多日。
2. **跨天才通知**（温和节点），当天内重排零通知——已与用户确认。
3. **Mongo 无跨文档事务**：插队/顺延是「读队列→改多条→写回」，需顺序执行 + 冲突校验 + 失败补偿（同一工程师单日队列冲突概率低，可接受）。
4. **历史数据回填**：存量工单无 `scheduledDate/scheduledTimeSlot`，需一次性反推，否则列表/详情显示为空。
5. **客户侧文案隔离**：内部真实原因与客户可见措辞两层分离，模板固定，防止「因有人插队」这类措辞外泄。
