# 角色权限分配方案（面向用户视角）

> 目标：让每个角色登录后，默认就能看到「该看到的页面」，观感合理；同时保留超级管理员「自主设置」的能力。
> 本文档是可执行方案，含：现状诊断、目标角色模型、页面可见性矩阵、权限粒度设计、前后端改动清单、数据迁移、待确认事项。

---

## 一、现状诊断（已核对数据库 `hrcms_test` 与代码）

1. **权限树缺「财务管理」节点**：`permissions` 集合只有 9 个节点，`财务管理(id=10)` 与子项 `共享文件(101)`、`资产管理(102)` 不存在。
   - 根因：`seed.py` 只在集合为空时插入权限，没有幂等迁移，老库补不进新增节点。
2. **角色里存在孤儿权限 id**：`admin/business/logistics` 写着 `101,102`，但权限集合里没有，后端 id→code 映射时被丢弃，财务菜单显示不出来。
3. **陈旧角色混杂**：库里实际 10 个角色，种子只定义 6 个。多出的 `sales / support / operator / finance` 是历史残留；其中 `finance` 角色权限只有 `[1,2]`（概览+需求单），**财务角色没有财务权限**。
4. **「勾选和菜单不对应」**：`Roles.vue` 保存时用 `getCheckedKeys()` 把父分组 id（3/9/10）也一起存了；下次加载时父 id 被勾上会级联把整组子项全勾，导致界面与实际权限错乱。
5. **只读/导出权限缺失**：导出与归档功能后端已有，但都挂在 `repair:all`（全权）下，无法给财务「只调阅、只导出、不修改」。

## 二、目标角色模型（7 个角色）

陈旧角色处理：`sales`、`support` → 合并进 `business`；`operator`、`logistics` → 合并为 `operation`；`finance` → 修复扶正。

| # | 角色 | code | rank | 来源/处理 |
|---|---|---|---|---|
| 1 | 超级管理员 | super_admin | 0 | 保留（内置，禁删） |
| 2 | 管理员 | admin | 1 | 保留（内置，禁删） |
| 3 | 业务 | business | 2 | 吸收 `sales`、`support` |
| 4 | 财务 | finance | 2 | 修复：补齐财务权限 + 调阅权限 |
| 5 | 运营（后勤+运营） | operation | 2 | `logistics` + `operator` 合并 |
| 6 | 工程师 | engineer | 2 | 保留 |
| 7 | 普通用户 | normal | 3 | 保留 |

## 三、权限树最终定义（含新增只读权限）

```
 1   dashboard        系统概览
 2   demand           需求单管理
 3   repair           售后报修管理（分组，仅树分组，不直接授权）
     31 repair:create     一键报修
     32 repair:my         我的报修 / 工单
     33 repair:all        所有工单（全权）
     34 repair:schedule   工程师排期（全权）
     35 complaints        投诉建议管理
     36 contact           联系我们配置
     37 repair:audit      工单调阅/导出（只读+导出）  ← 新增
 4   products         产品中心
 5   news             新闻中心
 6   honors           荣誉与相册
 7   cases            合作伙伴与案例
 8   config           全局配置
 9   system           系统管理（分组）
     91 system:users      成员管理
     92 system:roles      权限设置
     93 system:logs       操作日志
10   finance          财务管理（分组）
    101 finance:files     共享文件
    102 finance:assets    资产管理
```

- `repair:audit`（工单调阅/导出）：授予「查看所有工单（含归档）+ 查看排期 + 导出」的**只读**能力，无任何写操作。
- 父分组 id `3/9/10` 仅作树分组，**不存入角色权限**（保存时前端叶子化 + 后端过滤双重兜底）。

## 五、权限粒度设计（只读/导出怎么落地）

现状：写操作接口都挂在 `repair:all` / `repair:schedule` 上，没有只读档。

新增 `repair:audit`（只读+导出），后端把**读接口**改成「全权 或 调阅」均可访问，**写接口**仍只认全权：

| 接口 | 现状守卫 | 目标守卫 |
|---|---|---|
| GET `/repairs`（列表） | repair:all | repair:all **或** repair:audit |
| GET `/repairs/{id}`（详情） | repair:my | repair:my / repair:all / repair:audit |
| GET `/repairs/stats` | repair:all | repair:all / repair:audit |
| GET `/repairs/export`（导出 Excel） | repair:all | repair:all / repair:audit |
| GET `/repairs/schedule`（排期查询） | repair:schedule | repair:schedule / repair:audit |
| GET `/repairs/engineers`（工程师列表） | repair:all | repair:all / repair:audit |
| POST/DELETE `/repairs/schedule`、`assign`、`complete`、`fee`、`rework`、`transfer`、`confirm`、`progress` | 全权 | **维持不变（仅全权）** |

前端对应：`AllTasks.vue` / `EngineerSchedule.vue` 在「仅 repair:audit」时隐藏指派/进度/完结/费用/返修/转单/确认归档/创建排期等按钮，只保留「查看 + 导出」。

## 八、数据迁移（一键，幂等）

在 `run_seed` 内调用，随后端启动自动执行，无需手工操作：
1. `_migrate_permissions`：补齐 `10/101/102` + 新增 `37`。

## 十二、页面调整与新增方案（对标「通用后台管理系统」）

> 设计三原则：**便捷**（少点、少找、一步到位）、**易用**（不学习、不犯错）、**直观**（登录即所见即所得）。
> 现状判断：业务页已齐全，但「工作台个性化、待办通知、字典、个人中心、系统设置」等管理底座薄弱。

### 12.1 现状短板（对标通用后台标配）

| 通用后台标配 | 本项目现状 |
|---|---|
| 个性化工作台 | Dashboard 对**所有角色一视同仁**（KPI/快捷操作/待办硬编码，财务也能看到「系统用户数」「新增产品」） |
| 待办中心 + 通知 | 待办只在 Dashboard 一角，最多 3 类各 5 条，无角标、无站内信 |
| 数据字典 | 产品/投诉/资产/文件/工单/设备分类、部门、优先级**全硬编码**在前端与 seed |
| 个人中心 | 只有 header 下拉里的「修改密码」 |
| 系统设置 | 只有「全局配置」（对外网站），无对内系统设置 |
| 组织架构 | 部门硬编码在 seed 与资产下拉里 |
| 报表中心 | 只有 Dashboard 一张 7 天趋势图 |
| 回收站/软删除 | 删除全为硬删，误删不可恢复 |
| 全局搜索 | 无 |

### 12.2 调整现有（3 处）

1. **Dashboard 角色化（最该改，直观）**
   - 按 `roleCode` 渲染 KPI / 快捷操作 / 待办，消除「没权限的入口」：
     - **财务**：KPI=本月成本/已归档工单/待归档/资产总数；待办=待归档工单、成本核算；快捷=导出工单、成本核算。
     - **工程师**：KPI=待接单/处理中/今日排期；待办=我的待接单、进行中工单。
     - **运营**：KPI=产品/新闻/案例数 + 待处理投诉；快捷=新增产品、发布新闻。
     - **业务**：KPI=待跟进线索/待接单/待确认归档。
     - **普通用户**：KPI=我的报修/处理中；快捷=一键报修。
2. **Header 右侧补入口（便捷）**：通知铃铛（带未读角标）+ 全局搜索（Ctrl+K）+ 头像进个人中心。
3. **权限分配页 UX**：沿用第九节。
